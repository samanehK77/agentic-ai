# Observability and audit log (Batch 09)

An append-only audit log answers "what happened to this question?" from submission to outcome, including runs that failed. It records **metadata only**: counts, codes, durations, chunk ids and a configuration fingerprint. There is **no e-mail or report feature**: Gmail summaries from the SPEC were deliberately not implemented (optional feature), and sign-in stays at the scopes `openid email profile`.

Not production-ready and not clinically validated; this is a development and teaching setup.

## What is stored and where

| Place | Content | Lifetime |
|-------|---------|----------|
| `audit_events` (this document) | one row per event, metadata only, append-only | kept until an operator removes it (see Retention) |
| `chat_messages.trace` (Batch 08) | the node trace of one stored answer, a per-message snapshot | with the message |
| server log | one safe line per event of interest (ids, codes, durations) | log rotation |

The audit log and `chat_messages.trace` are made from the **same trace objects** the workflow produces (`GraphDeps.collected`, see below): there is one source of truth. The difference is that the audit log also has the trace of runs that failed (nothing is stored in `chat_messages` for them) and events outside the question flow.

## Table `audit_events`

| Column | Notes |
|--------|-------|
| `event_id` | uuid, primary key |
| `occurred_at` | timestamptz (the server's Python clock; node events use the node's own start time) |
| `correlation_id` | uuid generated by the **server** once per question or action; indexed. A client-supplied `X-Request-ID` is never reused for it |
| `request_id` | the (sanitized, at most 64 characters) request id, stored separately |
| `user_id` | uuid, nullable, `ON DELETE SET NULL` (rows survive user deletion; also null for failed sign-ins) |
| `session_id` | chat session uuid, nullable, no foreign key (no cascading delete) |
| `event_type` | one of the 14 types below (CHECK) |
| `outcome` | `ok`, `error`, `denied`, `skipped` (CHECK) |
| `error_code` | the standard API error code or a reason code |
| `latency_ms` | integer >= 0 |
| `seq` | order inside one batch (events are shown by `occurred_at, seq`); added because node timestamps have millisecond precision and can tie |
| `metadata` | jsonb object, at most 4096 bytes (CHECK), only the keys below |

Indexes: `(user_id, occurred_at)`, `(session_id, occurred_at)`, `(correlation_id)`, `(event_type, occurred_at)`.

**Append-only in the database:** a trigger rejects every `DELETE` and every `UPDATE`, except the one change PostgreSQL itself makes through `ON DELETE SET NULL` when a user is deleted (`user_id` from a value to NULL, every other column unchanged). Limits, stated honestly: the table owner can still drop the trigger, and `TRUNCATE` is not blocked. Real protection needs a separate application database role without UPDATE/DELETE grants.

## Event catalogue and allowed metadata keys

Every event type has its own Pydantic model (`backend/app/audit/events.py`) with `extra="forbid"`. Strings are at most 120 characters and may only contain letters, digits and `_ . : / -` (no spaces, no `@`), and strings that look like an IPv4 or IPv6 address are rejected. Numbers are bounded, lists are capped (chunk ids at most 20), the whole payload is at most 4096 bytes. Anything else is rejected: a warning is logged with the event type and the **key names only**, never the value, and the rejection is counted like a failed write.

| Event | When | Allowed metadata keys |
|-------|------|-----------------------|
| `sign_in_succeeded` | Google callback succeeded | `role` |
| `sign_in_failed` | callback failed | `reason` (`access_denied`, `state_invalid`, `token_invalid`, `email_unverified`, `not_configured`) |
| `sign_out` | logout | none |
| `patient_viewed` | `GET /api/patients/{id}` | `patient_id` (synthetic `P-nnn`) |
| `session_created` | `POST /api/sessions` | `patient_id` |
| `question_submitted` | a question passed the ownership check | `question_chars`, `mode`, `idempotent`, `config_fingerprint`, `model`, `prompt_version`, `retrieval_threshold`, `top_k`, `embedding_model`, `embedding_fingerprint`, `chunking_version` |
| `node_executed` | one per workflow node (skipped nodes with outcome `skipped`) | `node`, `status`, `reason_code`, `counts` (flat numbers), `chunk_ids` |
| `retrieval_executed` | after each search | `attempt`, `top_k`, `threshold`, `chunks`, `chunk_ids`, `evidence_level` |
| `llm_request` | the model call (also when it failed) | `model`, `config_fingerprint`, `prompt_tokens`, `completion_tokens`, `retries`, `repair_attempted`, `status` |
| `citation_validated` | citation check | `citations`, `verified`, `unsupported_claims`, `sections` |
| `answer_returned` | the run ended with an answer, or a replay of one | `result` (`answered`, `no_evidence`, `unsupported`, `crisis`), `message_id`, `classification`, `llm_called`, `replayed` |
| `pipeline_error` | the run failed (any `ApiError`, or `internal_error`) | `failed_node`, `retrieval_chunks` |
| `access_denied` | another user's session, or a role refusal | `route` (the route function name), `reason_code` (`not_owner`, `role_required`) |
| `feedback_submitted` | student feedback | `message_id`, `rating`, `reason` |

**Configuration fingerprint.** `config_fingerprint` is the first 12 hex characters of a SHA-256 over the model, prompt version, retrieval threshold, `top_k`, the embedding fingerprint and the chunking version. The readable values travel next to it. The embedding fingerprint and chunking version are stored as short hashes, because their readable forms contain `@`, `|` and `=`, which the metadata rules do not allow. The model name is the configured one (for a local model, for example `qwen3.5-16k`).

## What is never logged, and why

The question, patient text, chunk text, prompts, model answers, session titles, OAuth tokens and codes, API keys, passwords, e-mail addresses, IP addresses and user agents. They have no key in any event model, so they cannot be stored by accident, and a test scans every stored event of a full run (every answer kind, a failed run, sign-in, sign-out, feedback) for the question, chunk and patient text, titles, tokens, keys and e-mail and IP patterns. A question is represented by its length only. There is no catch-all HTTP logging middleware: only the events above are written.

## Writing events: transactions and failure behaviour

* **Own transaction.** `AuditService` (`backend/app/audit/service.py`) is the only code that inserts. Each write opens its **own** session and commits, never the request's. Events therefore survive when the answer transaction rolls back (the answer is stored in a last short transaction; if that fails, the audit log still has the whole run and a `pipeline_error`).
* **Per question.** `question_submitted` is written at once, so a long local run shows as *running* in the timeline. Everything else is written in **one batch** when the run ends, whether it succeeded or failed. Node events appear when the run ends (a node trace is only complete then); the timeline says so while a question is running.
* **Partial trace on failure.** The graph wrapper appends every finished node's trace event to `GraphDeps.collected`, plus an `error` event for the node that failed, before re-raising. `pipeline_error` is written with that partial trace.
* **Fail-open.** If an audit write (or its validation) fails, the user's request is not broken: a safe line `audit_write_failed type=... error=<exception class>` is logged (never the exception text or a value) and a counter is incremented. The counter is **per server process** (it restarts at zero) and is shown as `audit_write_failures` in the admin summary.
* **The one exception** is student feedback: it is the user's own action, so a failed save returns 503.
* **Idempotent replays** (same `Idempotency-Key`) write `question_submitted` and an `answer_returned` with outcome `skipped` and `replayed: true`; no node events, because nothing ran.

## Endpoints

| Endpoint | Access | Notes |
|----------|--------|-------|
| `GET /api/audit/timeline?session_id=` | signed in, **own session only** | groups by `correlation_id`, newest first, `limit`/`offset` count groups; foreign or unknown session 404; malformed id 422 |
| `POST /api/sessions/{sid}/messages/{mid}/feedback` | owner, CSRF | `{rating: helpful|not_helpful, reason?: fixed code}`; the first rating of a message stands (201 then 200 with `already_recorded: true`); reasons: `accurate`, `clear`, `good_sources`, `inaccurate`, `unclear`, `missing_sources`, `unsafe`, `other` |
| `GET /api/admin/audit/events` | admin | filters `event_type`, `user_id`, `outcome`, `date_from`, `date_to`; paginated |
| `GET /api/admin/audit/summary` | admin | counts per event type and day, error rate, no-evidence rate, p50/p95 answer latency, `audit_write_failures` |

Admin responses hold metadata only (they contain user ids, not names or e-mail addresses). Students get 403, signed-out callers 401. A group's `outcome` is `answered`, `no_evidence`, `unsupported`, `crisis`, `replayed`, `error`, `running` or `interrupted` (no final event after 10 minutes: the server probably stopped); single actions are `ok` or `denied`.

## Tracing one question end to end

1. The student's timeline (or `GET /api/audit/timeline`) lists the question with its `correlation_id`.
2. As an operator, with the correlation id:

```sql
SELECT occurred_at, event_type, outcome, latency_ms, error_code, metadata
FROM audit_events WHERE correlation_id = '<uuid>' ORDER BY occurred_at, seq;
```

3. You see, in order: `question_submitted` (with the configuration), the ten `node_executed` events (skipped ones marked), `retrieval_executed` (chunk ids), `llm_request` (model, tokens, retries), `citation_validated`, then `answer_returned` with the total latency, or `pipeline_error` with the standard error code and the failing node. The `request_id` column joins the event to the server log line and the `X-Request-ID` header of the response.

## Retention

Nothing is deleted automatically in this batch (the trigger forbids it). Rows hold no personal content, but they do hold user ids, so a real deployment must decide a retention period and purge by a privileged maintenance job that disables the trigger on purpose. That job is not part of this project.

## Limits

* Event times come from the server process clock; with several server processes they could interleave slightly differently.
* The failure counter and the in-process idempotency lock are per process.
* Node events are written when a run ends, not live.
* Chunk ids and counts reveal which documents were retrieved, not what they say.
