# Proposals (not implemented)

Two ideas that could make a small local model more dependable. **Neither is implemented.** Each needs your approval first,
because each changes behaviour that Batches 07-09 test. Read the risks before deciding.

Evidence for the need: with the local model `qwen3.5-16k`, a complex comparison question once ended as `502 llm_bad_output`
after 147 s (the model produced an invalid section kind twice, so the one repair attempt did not help). The live evaluation in
`docs/EVALUATION_REPORT.md` counts how often this and the repair attempt happened; those figures describe that one small model
only.

## 1. Constrained JSON output (response schema sent to the model server)

**Idea.** Today the client asks for `response_format: {"type": "json_object"}` (any JSON object) and the validator checks the
shape afterwards (`app/llm/schema.py`). Ollama (installed here: 0.40.13) can constrain the generated text to a JSON Schema, so
section kinds and field names could not be invalid.

**What would change.** `DeepSeekClient.complete` would send `response_format: {"type": "json_schema", "json_schema": {...}}` built
from the existing Pydantic model, only when the server is local (the remote DeepSeek API does not take a schema and would keep
`json_object`), controlled by a new setting (for example `LLM_JSON_SCHEMA=true`, default off).

**Risks.**
* Server support differs by version and model; a server that ignores or rejects the field would silently lose the constraint or
  fail every call. It needs a startup/diagnostics probe and a clean fallback to `json_object`.
* Constrained decoding can be slower, and can force a well-formed but empty or low-quality answer (valid shape does not mean a
  useful or faithful answer). Validity of the **shape** is not validity of the **claims**: quote verification and unsupported-claim
  reporting stay necessary.
* Schema features (enums for section kinds, `maxItems`) must match what `validate_answer` accepts, or the two will disagree.
* More configuration to document and to test on every model change.

**Effect on tests (Batches 07-09).**
* `tests/test_llm_deepseek.py` (lines asserting `payload["response_format"] == {"type": "json_object"}` and its absence cases) and
  `tests/test_answers_api.py` (the request-shape assertion near the top) assert the exact payload: with the setting **off** they
  stay valid unchanged; new tests would cover the **on** payload, the remote-provider payload, and the fallback.
* The repair tests (`test_malformed_json_gets_one_repair_attempt`, `test_a_schema_violation_is_repaired_with_field_names_only`,
  `test_still_bad_after_the_repair_is_a_502`, the empty/truncated test) keep working because the mock server ignores the schema;
  they would still pass as written. Audit tests (`test_audit_pipeline`) and the e2e tests are unaffected.
* Net: no existing test has to change if the feature is off by default; about 6-8 new tests are needed.

**Before/after plan (needs your approval for the model calls).** Run the same model-requiring runs (the 14 questions in the
`rag` and `both` modes, plus `general_knowledge`, about 30 runs that reach the model) twice with
`python -m app.eval_system run --live`, once with the setting off and once on, same day, same model state. Compare: valid JSON on
the first try, share needing the repair attempt, share ending as 502 or timeout, median latency and tokens per second, quote
verification share and unsupported claims. With about 30 runs per arm, only large differences mean anything; report both arms in
full including failures. Expected cost: about 60-90 minutes of model time for both arms.

## 2. "Evidence only" fallback instead of a 502

**Idea.** When generation fails after the repair attempt (`llm_bad_output`), return the retrieved chunks the model was given,
clearly labelled **"not generated by the model"**, instead of an error. A student would still see sources.

**What would change.** The answer service would catch `llm_bad_output` after the repair attempt and return `201` with a response
whose `generation.llm_called` is true, a new `safety.flags` entry such as `generation_failed_evidence_only`, no sections or
citations written by a model, and the evidence list; the frontend would render a visible banner; the audit log would record a
new `answer_returned` result (for example `evidence_only`).

**Risks.**
* **Misreading.** Students may take raw chunks for an answer. The label must be unmissable, the response must not contain
  sections of kind `research_finding`, and nothing may look cited.
* **Honest accounting.** A fallback hides model failures from the 502 count unless the audit and evaluation report them
  separately; otherwise the apparent reliability goes up while the model got no better.
* **Contract change.** `POST .../messages` currently stores nothing on failure and returns the standard error; a fallback would
  store a message, change idempotent replay (the key would replay the fallback), and add a new `result` value to the audit
  catalogue and its allowed metadata.
* **Safety.** Chunks flagged `possible_injection` must stay excluded; the safety screen and unsupported-request routing must run
  before it, exactly as today. Documents are copyrighted: the existing per-answer chunk limits must not be loosened.

**Effect on tests (Batches 07-09).**
* **Must change:** `tests/test_answers_api.py::test_still_bad_after_the_repair_is_a_502` and
  `::test_empty_or_truncated_provider_output_is_repaired_once_then_502` (they assert `502` and that nothing is stored), the
  `bad_output` case in `tests/test_audit_pipeline.py::test_a_failed_model_call_leaves_pipeline_error_and_the_partial_trace` (it
  expects `pipeline_error` and no stored message), and the `llm_bad_output` handling in `app/eval_system.py` / its tests
  (failed runs are counted by error code).
* **Must be extended:** the audit event catalogue test (`test_audit_events.py`: new `result` value), the privacy scan (the
  fallback response contains chunk text, which the audit log must still not hold), the e2e invariants (a fallback must have no
  citations), the OpenAPI/API docs.
* **Unchanged:** timeouts, the busy model (503), unsupported requests and no-evidence paths, all auth and isolation tests.
* Net: about 3 existing tests change meaning, which is why this needs your explicit decision rather than a quiet edit.

**Plan if approved.** Add the fallback behind a setting (default off), change the 3 tests to run both settings, add the audit
and frontend pieces, and re-run the live evaluation to show 502 share versus fallback share separately.
